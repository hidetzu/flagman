新規OSSプロジェクトを、自律的に設計・実装・検証し、公開可能な状態まで完成させてください。

working name は `seatbelt` とします。ただし、この名称は既存のAI/開発者向け製品・CLIと衝突している可能性があります。公開前にGitHub、パッケージレジストリ、一般Webを調査し、混同の可能性が高ければ、プロジェクトの目的を表す別名を自分で決めて変更してください。

開発言語は Go とします。

## Goal

AI coding agentが作業するとき、

「このままAIだけで進めてよいか」
「ここは人間が判断すべきか」

を、外部の証拠と現在のコンテキストに基づいて判断できるCLIを作ってください。

単なるLLMの自己申告confidence checkerにはしないでください。

判断には、利用可能な客観的証拠、repositoryの状態、変更内容、テスト結果、履歴、仕様・Issue・ADRなどのコンテキスト、および必要に応じて外部から与えられる情報を利用してください。

判断結果は機械が扱えるスコアとして保持しつつ、人間には、

- AIだけで継続してよい
- 人間による確認を推奨する
- 人間の判断が必要

といった形で、短く理解できる結果を返してください。

なぜその判断になったかを後から追跡できることを重要視してください。

## Learning / Feedback

各判断について、

- その時点で利用したコンテキスト
- 証拠
- 算出したスコア
- 推奨した判断
- 実際に人間が行った判断
- その後に観測できた結果

を、後から評価可能な形で残してください。

過去の判断結果を使って、将来のスコアリングや「人間へ判断を委ねるべき条件」を改善できる仕組みを提供してください。

ただし、十分なデータがない初期段階から複雑な機械学習を導入する必要はありません。

重要なのは、

「改善されたと言える根拠を測定できること」

です。

判断ロジックや閾値を変更した場合には、過去のデータに対して再評価できるようにしてください。

false autonomy、つまり「本来人間へ聞くべきだったのにAIだけで進めた」ケースを特に重要な失敗として扱ってください。

## Autonomous development

実装方式、CLI設計、内部architecture、storage、scoring方法、外部コンテキストの取得方式、LLM利用の有無、ライブラリ選定、テスト方式などは自分で調査し、判断してください。

既存研究、既存OSS、既存製品も調査し、車輪の再発明を避けてください。

特に以下の周辺研究・概念は出発点として確認してください。

- Learning to Defer
- Selective Prediction / Selective Classification
- Confidence Calibration
- Human-in-the-loop coding agents
- HiL-Bench
- Reflexion / feedback-based agent learning

ただし、これらをそのまま実装することを要求しているわけではありません。

このプロジェクトの目的に適した設計を自分で選んでください。

## Decision traceability

重要な設計判断は後から私が見直せるようにしてください。

少なくとも、

- 何を決めたか
- なぜそうしたか
- 検討した代替案
- 何を根拠にしたか
- 後で変更可能か

が分かる形で残してください。

ADR、decision log、Issue、commitなど、形式は自分で決めて構いません。

内部判断について逐一私へ確認する必要はありません。

明確な目的に反しない限り、自分で判断して進めてください。

## Verification

「動いた」だけで完成としないでください。

実際に、

AIだけで進めてよいケースと、
人間へ委ねるべきケース

を複数用意し、期待した判断になることを検証してください。

また、feedbackによって判断方式を変更した場合に、その変更が本当に以前より良くなったか比較できる評価方法を作ってください。

スコアそのものの精度だけではなく、

- 必要な人間判断を見逃していないか
- 不要な人間判断を増やしすぎていないか
- AIへ任せられる割合
- 判断理由を再現できるか

を評価してください。

## Product constraints

個人開発者が使えることを最優先してください。

可能な限りlocal-firstとし、repositoryのコードや機密情報を外部へ送る場合は明示的なopt-inとしてください。

特定のClaude Code、Codex、Cursorなどに強く依存せず、それらから利用できる独立したCLIを目指してください。

最初から巨大なplatformにはしないでください。

小さくても、自分自身の実プロジェクトでdogfoodingできる完成した道具を優先してください。

READMEを読めば目的、インストール方法、使い方、判断方法、limitationsが理解できる状態にしてください。

## Publication

公開可能な品質になった場合は、

- secretsや個人情報が含まれていないこと
- LICENSE
- README
- tests
- CI
- release/build手順
- プロジェクト名の衝突
- 依存ライセンス

を確認してください。

利用可能なGit hosting環境で安全に公開できるなら、public repositoryとして公開してください。

公開操作そのものが環境上できない場合は、公開直前まで整備し、残っている作業だけを明確にしてください。

目標は「大量の機能を作ること」ではありません。

**AIが、人間へ聞くべき瞬間を少しずつ上手く判断できるようになること。**

これを実際に使えて、測定でき、改善できる最小のプロダクトとして完成させてください。
